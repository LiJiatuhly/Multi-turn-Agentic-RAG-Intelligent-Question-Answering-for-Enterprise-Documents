完整版 · A三个本质不同

①　容错率极低 —— 目标从“答得好”变成“不能答错”

  • 通用场景答错只是体验差；医疗场景答错可能影响临床判断或用药决策，代价不可逆。
  • 直接后果是评估重心不同：医疗第一位是 faithfulness（答案严格基于检索证据）和可追溯性（每句结论能溯源到具体文档），而不是答案的流畅或相关性。
  • 我的对应：整条链路证据优先—— ReAct 循环强制先检索再作答，首轮就注入指令禁止模型凭训练知识硬答；证据不足走 fallback，宁可说“材料不足”也不编。
  • 加一句：医疗要的不是“什么都能答的 AI”，而是“知道自己什么时候不该答的 AI”——拒答机制的价值不低于生成质量。

②　数据敏感 + 强合规 —— 架构选型受硬约束

  • 患者隐私和审计要求让“数据不出域”往往是准入前提，不是优化项。
  • 后果是架构自由度被压缩：嵌入模型 / 大模型能否调外部 API、检索层要不要角色级权限过滤、全流程要不要审计日志——通用场景可选，医疗是门槛。
  • 我的对应（亮一个细节）：稀疏检索用本地 FastEmbedSparse，不依赖外部 API；稠密侧建库做了维度校验，换模型维度不匹配会直接报错提示重建而非静默出错，所以迁移到私有化部署的嵌入模型是可控的。
  • 体现：我知道医疗场景下“能不能用”先于“效果好不好”。

③　领域高度垂直 —— 通用 RAG 直接搬一定不好用

  • 医疗文档（药品说明书、临床试验报告、SOP、检验方法、诊疗指南）有两个特点：术语体系专业且歧义多（通用名 / 商品名、大量缩写、同义表达），信息强依赖语境（一个剂量数值脱离“适应人群 / 给药途径 / 禁忌”就变味）。
  • 恰好对应我下功夫最多的两块：术语和数字 → 混合召回（纯稠密向量对专有名词、编号、剂量数字不敏感，BM25 补盲区，RRF 融合）；语境不能断 → 父子分块（小块精确定位、不够时捞回完整父块补语境，避免断章取义——这在医疗文档里价值比普通文档高得多）。

  • 业务结构决定它的 AI 问题最有意思：罗氏诊断 + 制药双支柱，数据链条从“检验结果”贯通到“用药决策”——正是多跳推理最有价值的地方（某指标异常 → 关联病因 → 对应指南和药物 → 建议复查），一次检索答不了，必须拆解 + 多步检索，正是我两级架构做的事。

延伸②为什么自己做 RAG，而不用开源方案？
⚠ 这题的题眼（先看）
它很可能在测你会不会“重复造轮子”。你全程其实都在用开源（LangChain / LangGraph / Qdrant / FastEmbed），所以第一句必须先划清边界——“我用的全是开源组件，只是没用开箱即用的一站式方案”，否则面试官会误以为你从零造轮子。另外别说“开源模型不适用所有场景”，模型和方案是两回事，会扣分。
答题思路
先澄清边界 → 情境（起点是开箱方案）→ 卡点（撞到三堵墙）→ 解决（三改造）→ 收获（落点）→ 边界（不过度工程）。
完整版

①　先澄清（第一句就说）

  • 我不是不用开源，底层组件全是开源：LangChain / LangGraph 编排、Qdrant 向量库、BM25 / FastEmbed 稀疏检索。
  • 我没直接用的是“开箱即用的一站式问答方案”（如 Dify、RAGFlow 这类平台，或 LangChain 现成的 RetrievalQA 链）。准确说：我在开源组件之上自己做了编排层，不是从零造轮子。

②　情境 —— 起点就是开箱方案：最初跑通的就是最朴素那套（检索一次 → 塞进 prompt → 生成），用真实企业文档一测，问题立刻暴露。

③　卡点 —— 撞到三堵墙，且都不是调参能解决的

  • 复合问题漏答：一个问题常含两三个子问题，单轮检索只覆盖一个，答案漏一半；开箱方案流程固定，没有“拆解 + 多次检索”的口子。
  • 检索不准：纯稠密向量对专有名词、编号、数字不敏感，而这些恰恰最关键；开箱方案默认单路语义检索。
  • 分块两难：块大了整块向量被稀释、检索不准；块小了信息不全；固定分块策略下无解。

④　解决 —— 三堵墙对应三个改造

  • 换 LangGraph 显式状态图做两级架构：外层拆解 + 并行调度 + 汇总，内层 ReAct 循环由模型自己判断证据够不够。
  • 检索层混合召回：稠密 + BM25 两路并行、RRF 融合、互补盲区。
  • 分块做父子结构：子块进库保精度、父块单独存按 ID 取；关键一步——我把“取父块”做成模型可自主调用的工具而非固定流水线，小块够答就不浪费 token。这种控制粒度开箱方案给不了。
  • 附带：预算护栏、上下文压缩、子问题故障隔离——这些在开箱方案里都是黑盒。

⑤　收获 —— 这题的落点，一定要说

  • 自己搭一遍最大的价值不是“我会写 RAG”，而是效果不好时我知道该拧哪个旋钮：是检索漏了（context recall 低），还是检索对了但生成飘了（faithfulness 低）。
  • 用开箱方案效果不好时，你基本只能换模型、改提示词；拆开搭过一遍，才能把问题定位到具体哪一层。而垂直领域——尤其医疗这种文档结构和术语特殊的场景——几乎必然要定制，这个定位和改造能力绕不过去。

⑥　边界（加分，显示不过度工程）：如果是公司生产环境、需求标准、要求快速上线，我会优先选成熟方案，不会为了自研而自研。自研的价值在于需要深度定制和精细可控的场景。

精简版 · 临场兜底
一句话：我用的全是开源组件，只是没用开箱即用的一站式方案，因为它满足不了我撞到的三个具体问题。
起点：最朴素的“检索一次就答”。　三堵墙：复合问题漏答 / 关键词与数字检索不准 / 分块大小两难。

三Agent / 大模型 八股题库Q & A Bank
Q1openclaw 这类开源 coding agent 的底层原理是什么？一次任务是怎么跑起来的？

Agent 的底层不是一个大提示词，而是模型 + 工具 + 循环 + 上下文工程。模型负责每一步决策，工具是它读文件、搜索、写文件、跑测试的“手”；agent loop 让它“决策 → 执行 → 观察 → 再决策”地转圈，直到任务完成。工程上最关键的是：上下文管理要按需检索、加压缩；任务要拆解；状态要可持久化；同时用权限审批和 git worktree 做隔离，守住安全边界；靠把错误循环回灌来做恢复。它跟 MCP 和大模型 API 的关系是——大模型 API 提供推理能力，MCP 这类协议提供标准化的工具接入，Agent 框架本身是把它们编排起来的那一层。

Q2为什么大模型的主流架构是 Transformer，而不用以前很火的 CNN、RNN？

一句话概括：Transformer 靠自注意力机制同时解决了三个关键问题——长距离依赖、并行计算、规模化训练。更完整地说：

  • ①　长距离依赖：RNN 靠时序逐步传递信息，序列一长，早期信息在反向传播时容易梯度消失 / 爆炸，很难建立远距离词之间的关系；CNN 靠局部卷积核，感受野受核大小限制，要堆很多层才能覆盖长距离。而自注意力让序列里任意两个位置直接交互，无论多远都是一步可达，长距离依赖天然被捕捉。
  • ②　并行计算：RNN 必须一个时间步算完才能算下一步，本质是串行的，训练慢、吃不满 GPU；Transformer 对整条序列的自注意力可以一次性并行算出来，非常契合 GPU/TPU 的大规模矩阵运算，训练效率高得多。
  • ③　规模化训练（Scaling）：结构统一、可并行、对硬件友好，使它能稳定地把参数量、数据量、算力一起往上堆，并表现出可预期的 Scaling Law，这是 CNN/RNN 很难做到的，也是“大”模型能成立的前提。

补充：代价是自注意力对序列长度是 O(n²) 的计算 / 显存复杂度，所以后续才有各种稀疏 / 线性注意力、FlashAttention、长上下文优化等改进。

批注已按要求补充展开。要点顺序仍是：长距离依赖 / 并行计算 / 规模化训练。
Q3Transformer 自注意力机制的 Q、K、V 分别是什么？

Q（Query）是当前位置发出的查询，表示它要从上下文里找什么信息；K（Key）是每个位置暴露出来的匹配特征，表示它可以被“怎样找到”；V（Value）是每个位置真正提供的内容，表示一旦它被关注，应该贡献什么信息。self-attention 的过程就是：用 Q 和 K 计算注意力分数，再用这些分数对 V 做加权汇总。

批注表述准确。可补一句机制细节：分数一般是 QKᵀ 缩放（除以 √dₖ）后过 softmax，再加权求和 V。
Q4稠密向量检索和稀疏检索有什么区别？

稀疏检索基于词项统计（如 BM25/TF-IDF），适合精确匹配、可解释检索和专有名词场景；稠密检索基于语义向量，适合同义表达、模糊问题和泛化召回。真实 RAG 系统里常用混合召回，再用 Reranker 统一排序，通过召回命中率和忠实度等指标来验证效果。

批注进阶展开见第四部分 Q7：稠密 / 稀疏各自优缺点 + RRF 原理。
Q5RAG 系统怎么做？

向量数据库只是 RAG 的一个组件。生产级 RAG 的分层是：

  • ①　数据治理：先做文档清洗、版本、权限和元数据管理；
  • ②　检索层：关键词、向量、重排（rerank）组合；
  • ③　生成层：控制证据引用和拒答；
  • ④　评估层：看召回、重排、忠实度和引用准确率；
  • ⑤　上线后闭环：把用户反馈和 badcase 回流到知识库和测试集。

4.3　四道预判必答题
Q6为什么选 LangGraph，而不是纯 LangChain 或别的框架？

一句话：我的系统需要三个能力——循环（Agent 反复思考 → 检索）、并行（多子问题 Fan-out/Fan-in）、能暂停等人补充（澄清）。这三个恰好都是 LangGraph 的强项，其它方案要么做不了循环，要么控制粒度不够。

  • 纯 LangChain（LCEL 链）：LCEL 本质是有向无环图（DAG），天然不支持“循环”。而我内层 Agent 的“思考 → 检索 → 再思考”就是个 while 循环，还要在预算耗尽时刹车——用链很别扭。
  • LlamaIndex：更偏检索 / 索引这一层，做定制的 Agent 编排、精细的状态控制不如 LangGraph 灵活。
  • CrewAI / AutoGen：抽象层级更高，“多 Agent 协作”开箱即用，但代价是看不清也控制不了每一步状态怎么流转。我需要精确管预算、路由、上下文压缩，高层框架反而碍事。（横向对比见 Q12。）

LangGraph 四个关键能力对应我项目里的用法：① 显式状态机 + 条件边，全图岔路就两个路由函数，好调试；② 原生支持循环，子图检索循环靠条件边实现；③ Send API 做并行，一次发射多个子图并行跑、跑完自动汇合；④ Checkpoint + Interrupt，能在澄清节点前暂停整张图、等用户补充、再从断点恢复（human-in-the-loop 的基础）。

追问“两级状态机为什么不用一张图？” 答：子图有独立的 AgentState 和独立的 messages 列表，每个子问题从空白草稿纸开始、互不干扰；主图只管拆分和汇总。混在一张图里，几个并行子问题的对话消息会串在一起。
Q7混合检索里，稠密和稀疏各自的优缺点？RRF 的原理和好处？

混合检索 = 语义检索（稠密向量）+ 关键词检索（稀疏向量 / BM25）两路一起跑，再用 RRF 融合。这两路各有盲区，合起来互补。

  • 稠密向量（我用智谱 embedding-3，2048 维）：优点是懂语义，“报销的最高额度”能匹配到文档里的“费用上限”，抗同义、抗改写；缺点是对精确关键词、专有名词、编号、数字不敏感，这些在嵌入空间里区分度低，容易漏。
  • 稀疏向量 / BM25（我用本地 FastEmbedSparse）：优点是精确关键词匹配，专有名词 / 型号 / 数字命中率高、可解释、本地跑不用 GPU/API；缺点是完全不懂语义，“汽车”和“轿车”匹配不上（词汇失配）。

一句话记：稠密懂意思但记不住词，稀疏记得住词但不懂意思，合起来正好互补。

RRF（Reciprocal Rank Fusion）原理：对每个文档 d，得分 = Σ 1/(k + rankᵢ(d))，rankᵢ(d) 是 d 在第 i 路结果里的排名，k 是常数（常用 60）。直觉是：一个文档在任意一路排得越靠前得分越高，两路都靠前的最高。

好处（为什么不直接把两个分数相加）：稠密的余弦相似度和 BM25 分数根本不在一个量纲上，直接加权没意义还得费劲归一化。RRF 只用排名不用原始分数，天然对量纲免疫、不需要调归一化参数，非常鲁棒。我代码里就是把 QdrantVectorStore 设成 RetrievalMode.HYBRID 同时挂稠密和稀疏嵌入，由 Qdrant 内部做 RRF。

7B 进阶追问既然有 Reranker，为什么很多系统混合召回后还要再重排？（呼应第三部分 Q4）——RRF 是无监督的“排名融合”，只看两路各自的名次、不看 query 与文档的深层匹配；Reranker（如 cross-encoder）是把 query 和每个候选拼在一起算相关性，更准但更慢。工程上常见分工：先用混合召回 + RRF 粗召回一批（快、召回率高），再用 Reranker 对这批精排（准）。我的项目目前止步于混合召回 + RRF，如果要上生产、追求更高精排质量，Reranker 是自然的下一步——这点我可以主动说，显示我知道边界在哪。
Q8怎么处理长文本？父子分块具体怎么实现？

先点核心矛盾：分块大小是两难——块切大了，一次检索能给足上下文，但 query 只匹配到块里一小部分，整块向量被“稀释”，检索不准；块切小了，检索准但单块信息不全，答不上来。父子分块就是来化解这个矛盾的。

  • ①　切两层：文档先切成父块（大，按章节 / 大段），每个父块再切成子块（小，按句 / 小段）。
  • ②　只把子块进向量库：子块做嵌入进 Qdrant，每个子块 metadata 里带着它的 parent_id，检索匹配小块 → 精度高。
  • ③　父块单独存：完整父块存成本地 JSON 文件（ParentStoreManager 管理），文件名就是 parent_id，按 ID 直接读，O(1)。
  • ④　由小到大：先 search_child_chunks 搜到相关小块拿到 parent_id → 如果小块太零碎，再 retrieve_parent_chunks 把整个父块捞出来给模型。

我这个设计最有意思的一点（主动说，显示想得深）：我把“取父块”做成了模型可以自己调用的工具，而不是固定流水线——是否升级到父块，是模型根据小块够不够来决定的：小块能答就不浪费 token 取大块，不够才取。这比死板地“每次都取父块”更省更灵活。

追问“chunk size 设多大？” → 真实值（config.py）：子块 CHILD_CHUNK_SIZE=500、重叠 CHILD_CHUNK_OVERLAP=100；父块 MIN/MAX_PARENT_SIZE=2000~4000，即父块约为子块的 4~8 倍。子块留 100 字重叠是为了让相邻块共享边界句、避免检索漏掉跨块的句子。这些数字要能张口就答。另外父块为什么不进向量库？因为向量库定位是“存向量 + 简短 metadata 做快速相似度检索”，存大段父块又慢又占空间，父块只需按 ID 精确读取，用 JSON 文件最直接——这是“让每个组件干它最擅长的事”。
Q9怎么评估 RAG 系统效果？（RAGAS 框架）

RAGAS 用大模型当裁判，把 RAG 质量拆成“检索质量”和“生成质量”两块打分，好几个指标不需要人工标准答案，适合快速迭代。四个核心指标：

  • Faithfulness（忠实度）：答案是不是严格基于检索到的内容——反幻觉。不需要标准答案。
  • Answer Relevancy（答案相关性）：答案切不切题。不需要标准答案。
  • Context Precision（上下文精确率）：检索回来的相关内容排得靠不靠前。
  • Context Recall（上下文召回率）：该检索到的信息是不是都检索到了。需要标准答案。

为什么用它：它能把 RAG 的问题定位到底是“检索烂”还是“生成烂”——比如 faithfulness 高但 answer relevancy 低，说明检索对了但答偏了；context recall 低，说明检索漏了。

我的系统怎么给它喂数据：工具返回的检索原文是固定格式（Parent ID / File Name / Content），我在子图里用一个 _retrieval_contexts 函数把这些反向解析、抽出干净的检索上下文，随答案一路冒泡到主图，就能交给 RAGAS 算 context precision/recall。（有个细节值得说：上下文压缩会用 RemoveMessage 把原文烧掉，所以我特意在压缩前把检索原文备份进 retrieved_contexts 字段，保证评测拿得到“模型到底看了哪些原文”。）

诚实话术如果被追问“你的 RAGAS 分数是多少”：如实说这是个人项目，评估这块我做的是“预留了接口、把检索上下文按 RAGAS 需要的格式抽出来了”，但还没跑成完整的量化基准。可以顺势讲机制——“faithfulness 和引用来源是我最看重的，因为医疗场景不能容忍幻觉；混合召回对 context recall 的改善最直接，因为 BM25 补上了纯语义漏掉的关键词命中”。核心原则：说得清指标含义、讲得清机制，胜过背一个自己扛不住追问的分数。宁可承认“还没跑完整基准”，也不要编数字。
◆ 架构深挖弹药（面试官往下钻时用）
  • 怎么防 Agent 无限循环 / 烧钱？两道预算护栏 MAX_ITERATIONS=10（最多循环 10 圈）和 MAX_TOOL_CALLS=8（最多调 8 次工具），路由每轮检查，超了就转 fallback 强行作答；外面还有一道 LangGraph 全局兜底 GRAPH_RECURSION_LIMIT=50，防止图本身递归失控。计数器用 operator.add 累加而不是覆盖——这点很关键，覆盖的话计数永远到不了上限，就真无限循环了。
  • 上下文越来越长怎么办？compress_context 把冗长检索原文压成结构化摘要，同时用 retrieval_keys 记下“已搜过的词 / 取过的父块”写进摘要，提醒模型别重复检索。触发阈值不是写死的：基线 BASE_TOKEN_THRESHOLD=2000、每轮按 TOKEN_GROWTH_FACTOR=0.9 动态放宽。诚实一点可以补：token 数是用 tiktoken（cl100k）估的，对中文偏低估，而且没算 system prompt——但它只用来触发压缩，宁可晚压也不压崩，偏低无妨。
  • 检索阈值为什么敢设到 0.02（RETRIEVAL_SCORE_THRESHOLD）？这是我真踩过“检索总为空”的坑之后定位到的：HYBRID 模式下这个阈值卡的是 RRF 融合分（上限约 1.0），不是余弦相似度。只被一路（dense 或 sparse）命中的块 RRF 分很低，阈值一高就会被整批过滤掉、直接“搜不到”；中文场景 BM25 偏弱、主要靠 dense，所以特意压到很低。能讲清这一点，说明我分得清 RRF 分和余弦分——这是很多人会答错的地方。
  • 为什么结构化输出用 json_mode 而不是 tool calling？生成模型是智谱 glm-4.7，不支持强制 tool_choice，所以用 with_structured_output(QueryAnalysis, method="json_mode")；json_mode 偶尔返回脏类型，我在 schema 里加了 field_validator 容错（把字符串 "true" 转布尔、单字符串包成数组）。
  • 换嵌入模型会怎样？维度不匹配。建集合时会校验：已有维度 ≠ 当前模型维度就直接报错提示清库重建，而不是静默出错。
  • 并行子图会不会污染主对话历史？不会。子图每条消息都打了 name 标签，汇总时把带 name 的过滤掉，只留真实对话——这是“子图消息流回主图却不污染历史”的机制。
  • 某个子问题检索失败？工具不抛异常炸图，而是返回“暗号”字符串（NO_RELEVANT_CHUNKS / RETRIEVAL_ERROR），下游解析时过滤掉。故障隔离：一个子问题出问题不影响其它并行子问题。

模拟你的 RAG 项目是怎么设计的？为什么这样设计？
答题思路
是什么项目（定位）→ 解决什么问题 → 核心挑战 → 设计理念分点讲。先答到点子上，再补支撑。
完整版 · 约 2~3 分钟

一句话总纲：整个系统的设计主线，就是“把一个复杂的复合问题，先拆开、再并行地反复检索，最后拼成一个完整且可追溯的答案”。

先说定位和它要解决的问题。我这个项目是一个面向企业文档的多轮 Agentic RAG 问答系统。核心挑战在于：真实场景里用户的问题往往不是一句话就能检索到答案的——一个问题里常常包含好几个子问题，需要多次检索才能把完整答案拼出来。传统那种“检索一次 → 把结果塞进 prompt → 让模型生成”的 RAG，遇到这种复合问题就容易漏答或者幻觉。所以我整个设计，都是围绕“怎么让系统自己把复杂问题拆开、反复查、再拼完整”来展开的。

具体的设计理念，我分四点讲：

  • ①　把“一次检索”改成“模型自主的多次检索”，也就是 ReAct 循环。传统 RAG 检索一次就作答，问题一复杂证据就不够。所以我在内层让模型跑一个“思考 → 检索 → 再思考”的循环：每一轮模型自己判断手头证据够不够，不够就继续调检索工具，够了才作答，而不是拿到问题就硬答。这样答案是“查够了证据”之后才给出的，有据可依。
  • ②　复杂问题先拆解、再并行检索，也就是 Fan-out / Fan-in。一个复合问题直接丢给模型，几个子问题的检索会互相干扰，而且是串行的、慢。所以我在外层先把问题改写、拆成 1~3 个自包含的子问题，再用 LangGraph 的 Send 机制并行分发，每个子问题独立检索、互不干扰，最后汇总合成一段连贯回答。这样既保证了多跳问答的准确率，又靠并行把响应时间压了下来。
  • ③　用两级状态机分层——外层主图管调度，内层子图管检索。关键考量：如果把所有东西塞在一张图里，几个并行子问题的对话消息会串在一起、互相污染。所以拆成两级——外层只负责“理解问题 → 拆分 → 并行调度 → 汇总”，每个子问题交给一个独立的 Agent 子图，子图有自己独立的状态和消息列表，从一张空白草稿纸开始，彼此隔离。分层后每层职责单一，也更好调试。
  • ④　检索这一层做得比较扎实——混合召回 + 父子分块。检索准不准直接决定答案质量，所以做了两件事：一是混合召回，稠密向量懂语义但记不住专有名词和数字，稀疏检索（BM25）正好相反，两路一起跑、用 RRF 融合，互补盲区；二是父子分块，块切大了检索不准、切小了信息不全，所以子块进向量库做精确定位、父块单独存，命中小块后如果上下文不够，再把对应父块整段捞回来补全，避免长文档断章取义。

最后收一句。工程上我还加了一些护栏——给循环设预算上限防止无限检索烧钱、上下文过长就压缩、单个子问题检索失败也不会拖垮其它并行子问题。整体思路就是分层、可控、每一步检索都可追溯，这也是考虑到医疗这种低容错场景才特别强调的。

精简版 · 临场兜底
万一脑子一片空白，先把四个词抛出来当记忆锚点：多次检索 → 拆解并行 → 两级图 → 检索扎实
  • 定位一句：面向企业文档的多轮 Agentic RAG 问答系统。
  • 挑战一句：用户问题常含多个子问题，要多次检索才能拼出完整答案；传统“检索一次就答”容易漏答、幻觉。
  • ① 多次检索（ReAct）：模型自己判断证据够不够，不够就继续查、够了才答，不硬答。
  • ② 拆解 + 并行（Fan-out/Fan-in）：复合问题拆成 1~3 个子问题，用 Send 并行检索、互不干扰，再汇总。
  • ③ 两级状态机：外层管拆分调度，内层管检索，子问题状态隔离、互不污染。
  • ④ 检索扎实：混合召回（稠密 + BM25，RRF 融合）互补盲区；父子分块（子块精确定位、父块补全上下文）防断章取义。
  • 收尾一句：分层、可控、每步可追溯——医疗低容错场景尤其看重这点。

Q10“手写一个极简 LangChain”——它的核心抽象到底是什么？

这题考的不是背 API，而是你懂不懂 LangChain 把什么东西抽象成了积木。一句话：LangChain 的核心是 Runnable（可运行单元）+ 用管道 | 把它们串起来（LCEL），最典型的一条链就是 Prompt | Model | OutputParser。它把 LLM 应用拆成几类可组合的积木：

  • PromptTemplate：带变量的提示词模板，.format() 填参数生成最终 prompt。
  • Model（LLM / ChatModel）：对各家大模型 API 的统一封装，输入 messages、输出 AIMessage。
  • OutputParser：把模型输出的字符串解析成结构化对象（比如 JSON→pydantic，就是我项目里 with_structured_output 干的事）。
  • Runnable + LCEL：每个积木都实现统一的 invoke() 接口，并重载 | 运算符，于是能像管道一样串起来，还自动获得 batch / stream / async。

再往上：Memory（对话记忆）、Retriever（检索器）、Tool + Agent（让模型调工具）、Chain（把上面这些编排成流程）。

极简实现（讲清“管道”的本质，能手写这段就够了）：

class Runnable:                  # 所有积木的基类
    def invoke(self, x): ...     # 统一接口：输入→输出
    def __or__(self, other):     # 重载 | ，实现"管道"
        return Chain(self, other)

class Chain(Runnable):           # 把两个 Runnable 串起来
    def __init__(self, a, b): self.a, self.b = a, b
    def invoke(self, x):
        return self.b.invoke(self.a.invoke(x))  # 前一个输出喂后一个

class Prompt(Runnable):
    def __init__(self, tpl): self.tpl = tpl
    def invoke(self, vars): return self.tpl.format(**vars)

class Model(Runnable):
    def invoke(self, prompt): return call_llm_api(prompt)   # 调大模型

class JsonParser(Runnable):
    def invoke(self, text): return json.loads(text)

chain = Prompt("回答：{q}") | Model() | JsonParser()   # ← 这就是 LCEL
chain.invoke({"q": "报销上限"})                          # 一路 invoke 下去

收尾一句（拔高）：理解了这个，就明白 LangGraph 是在 LangChain 之上更进一步——LCEL 是“无环管道”，而 LangGraph 把它变成“能循环、能并行、有状态的图”，正好补上 Agent 需要的循环和分支。

Q11ReAct 范式是什么？（我项目内层子图跑的就是它）

ReAct = Reasoning + Acting，让模型把“推理”和“行动”交错进行，而不是一口气答完。经典形式是一个循环：Thought（想一下现在缺什么）→ Action（调一个工具）→ Observation（看工具返回）→ 再 Thought…… 直到它认为证据够了才给最终答案。

为什么有用：纯让模型凭记忆答容易幻觉；ReAct 强迫它“先去查证据、看到结果再决定下一步”，把外部工具（检索）接进推理链，答案就有据可依、可追溯。

对应到我的项目（讲得具体才可信）：内层 Agent 子图的 orchestrator 节点就是 ReAct 的循环体——每轮模型看手头材料，决定“再调检索工具”（继续 Act）还是“证据够了直接作答”（收敛退出）。我还做了两个工程强化：① 第一轮强制注入一条指令逼它必须先调 search 工具，杜绝跳过检索凭训练知识硬答；② 用 MAX_ITERATIONS / MAX_TOOL_CALLS 给循环设预算上限，超了就兜底作答，防止想太久停不下来。

加分点可以点出“经典 ReAct vs 现代实现”的区别：早期 ReAct 靠让模型输出 Thought:/Action:/Observation: 文本、再用正则解析，脆弱；现在主流是用模型原生的 tool calling（function calling）来表达 Action，结构化、更稳。我项目走的就是原生 tool calling 这条现代路线——模型在 AIMessage.tool_calls 里说要调哪个工具，框架 ToolNode 真的去执行，本质还是 ReAct 的“思考 - 行动 - 观察”循环。
Q12主流 Agent 框架横向对比：LangChain / LangGraph / LlamaIndex / AutoGen / CrewAI？
框架定位 / 抽象特点最适合
LangChain组件库 + LCEL 管道把 Prompt/Model/Parser/Retriever/Tool 抽象成可组合积木；擅长线性流水线，环和复杂状态较弱常规 RAG、链式流水线
LangGraph
（我用的）		显式状态机（图）原生支持循环、条件分支、并行(Send)、状态持久化、中断恢复；控制粒度最细，好调试Agent 循环、并行编排、human-in-the-loop

AutoGen
（微软）		多智能体“对话”把协作建模成多个 Agent 互相发消息（如 Assistant + UserProxy），支持 group chat、代码执行；高层、省心，但每步状态不透明多角色协作、自动写 / 跑代码
CrewAI角色化多智能体用“角色 + 任务 + 流程”组织多个 Agent，上手快、偏封装；底层控制不如 LangGraph快速搭多角色工作流原型

一句话总结（面试官问“你怎么选”时）：LangChain/LlamaIndex 偏“组件”，AutoGen/CrewAI 偏“多 Agent 高层封装”，LangGraph 偏“把流程显式画成可控的状态图”。我选 LangGraph 是因为我要的正是精确控制循环、并行和中断——这是高层多 Agent 框架给不了的粒度。如果需求是“几个角色自动协作写代码”，AutoGen 会更省事；但我的场景是“单问题深度检索 + 多子问题并行”，LangGraph 最贴。

关于 AutoGen若被追问细节：它的核心是“可对话的 Agent”——每个 Agent 有角色和系统提示，通过互相收发消息推进任务；UserProxyAgent 还能代替人执行代码 / 工具，配 group chat 可让多个 Agent 围绕一个任务讨论。和我的 LangGraph 方案的本质差异：AutoGen 把编排藏在“对话协议”里（谁该说话由框架 / 规则决定），我则把编排显式画成状态图（谁接谁、什么条件走哪条边，一目了然、可断点调试）。

三个短板的话术
话术 ①　「我们用 Pinecone/Milvus，你用 Qdrant 行吗？」
Qdrant、Pinecone、Milvus 是同一类向量数据库，核心概念完全相通：集合、稠密 / 稀疏向量、相似度度量、metadata 过滤、混合检索。我用 Qdrant 做过建库、维度校验、混合检索全流程，迁移到 Pinecone/Milvus 只是 API 层差异，几天就能上手。我特意用了 Qdrant 的 HYBRID 模式，对混合检索原理理解得比较透。
话术 ②　可视化（Tableau / Power BI）
诚实版：BI 工具我还没深度用过，但我用 Matplotlib/Seaborn 做过〔漂绿识别 / 情绪预测〕的结果可视化，数据可视化的思路是通的，Tableau/Power BI 我可以快速学。（今晚可选：20 分钟看个 Power BI 入门，至少能说出“拖拽式做交互仪表盘：连数据源 → 建关系 → 拉图表”。）
话术 ③　SQL
诚实版：SQL 我基础的单表查询已经比较扎实——SELECT、WHERE 条件筛选、ORDER BY 排序、常用字符串 / 日期函数都能独立写；多表 JOIN 和 GROUP BY 聚合正在系统补，增删改（INSERT/UPDATE/DELETE）是下一步。我不夸大，但补 SQL 对我不难：我有一套见效很快的学习方法（见第二部分延伸③），而且真正的数据管道能力我在 RAG 项目里是实打实做过的——PDF 抽取 → 清洗 → 切块 → 入库这条 ingestion 流程，概念上就等同一条 ETL。所以我更想强调的是“把数据从原始格式变成可用结构”的工程能力，纯 SQL 语法我能很快跟上。
按你的真实进度校准此话术已按“会查询 + ORDER BY、JOIN/GROUP BY 在学、增删改未学”写。如果面试前你把 INNER/LEFT JOIN 和 GROUP BY 练到能写基础语句（对数据岗这两个几乎必考，建议优先攻），可以把上面第一句直接升级成“单表查询 + 基础 JOIN + GROUP BY 聚合都能写”。
